================================================================================
PHASE 1: START CONTAINER (~2 min)
================================================================================
Open TERMINAL 1 on the Ubuntu host.

1.1) Check webcam device and verify the Docker image exists:

ls /dev/video*
docker images | grep ros2_fossbot_edu

  * Note the lowest video number (almost always /dev/video0).
  * If "ros2_fossbot_edu" is MISSING, build it first (takes 15-25 min):
      git clone https://github.com/LRMPUT/FOSSBotEduSim.git
      cd FOSSBotEduSim
      bash build_image.sh
  * If it ALREADY exists, cd into the FOSSBotEduSim folder:
      cd ~/FOSSBotEduSim

1.2) Start the container with display, NVIDIA GPU, and webcam access
     (Run from inside the FOSSBotEduSim directory):

xhost +SI:localuser:$(id -un)
XAUTH=/tmp/.docker.xauth
touch $XAUTH
xauth nlist :0 | sed -e 's/^..../ffff/' | xauth -f $XAUTH nmerge - 2>/dev/null
chmod a+r $XAUTH

docker run -it --rm \
    --name=ros2_fossbot_edu \
    --shm-size=1g \
    --ulimit memlock=-1 \
    --env="DISPLAY=$DISPLAY" \
    --env="QT_X11_NO_MITSHM=1" \
    --env="XAUTHORITY=$XAUTH" \
    --volume="$XAUTH:$XAUTH" \
    --volume="/tmp/.X11-unix:/tmp/.X11-unix:rw" \
    --volume="$(pwd)/ws_fossbot:/fossbot_ros2/ws_fossbot" \
    --device=/dev/dri:/dev/dri \
    --device=/dev/video0:/dev/video0 \
    --group-add video \
    --group-add $(getent group render | cut -d: -f3) \
    --gpus 'all,"capabilities=compute,utility,graphics"' \
    --env="NVIDIA_VISIBLE_DEVICES=all" \
    --env="NVIDIA_DRIVER_CAPABILITIES=all" \
    --network=host \
    --pid=host \
    --ipc=host \
    ros2_fossbot_edu \
    bash

  (If webcam is /dev/video2 instead of /dev/video0, change the --device line
   above AND edit cv2.VideoCapture(0) to cv2.VideoCapture(2) after cloning.)

================================================================================
QUICK TROUBLESHOOTING
================================================================================
- Left and right feel swapped?
  Open the file and swap "left" and "right" in classify_gesture:
    nano /fossbot_ros2/ws_fossbot/src/fossbot_gesture_control/fossbot_gesture_control/gesture_steering.py
  Then rebuild fast:
    cd /fossbot_ros2/ws_fossbot
    colcon build --packages-select fossbot_gesture_control
    source install/setup.bash

- Webcam doesn't open / black window?
  Run "ls /dev/video*" on the host. If it's /dev/video2, restart docker with
  --device=/dev/video2:/dev/video2, change cv2.VideoCapture(0) to (2), and
  rebuild with --packages-select fossbot_gesture_control.

- Thumb left/right not triggering easily?
  Hold hand slightly closer to camera, or lower 0.1 to 0.07 in "abs(dx) > 0.1",
  then rebuild with --packages-select fossbot_gesture_control.


================================================================================
CHEAT SHEET FOR SECTION 9 (ANALYSIS QUESTIONS — IF ASKED)
================================================================================
Q1: Why is stopping on unrecognized gestures safer than keeping the last command?
A1: Fail-safe design. If the camera drops frames, lighting changes, or you lower
    your hand in a panic, repeating the last velocity would cause an uncontrolled
    crash. Defaulting to a zero Twist guarantees an immediate stop whenever
    intent is unclear.

Q2: Why publish ~10 Hz even when the gesture doesn't change?
A2: The robot's controller uses a safety watchdog timeout (Lab 06): if no new
    /cmd_vel arrives within a short interval, it halts the wheels automatically
    in case the control node crashed or Wi-Fi dropped. Continuous publishing
    keeps the robot moving while a gesture is held.

Q3: One situation where classify_gesture misreads the hand, and how to fix it?
A3: Tilting or rotating the hand sideways/upside-down breaks the simple y-axis
    check (tip.y < pip.y assumes an upright hand). Fix: compare Euclidean
    distances from fingertip to wrist (landmark 0) against PIP-to-wrist distance
    (rotation-invariant), and require 3 consecutive identical frames before
    changing commands to filter jitter.

Q4: Practical differences between simulator and real robot?
A4: (Adjust to what you observe!) Typically: slight Wi-Fi latency, real floor
    friction/wheel slip and motor deadband at low speeds (0.2 m/s), and room
    lighting causing more landmark jitter than ideal Gazebo physics.
